How This Works, In Plain Language

OrderFlow runs entirely in the browser — no server, no database. It's essentially one HTML file that knows how to read a list of orders, think about them, and show the seller what to do.

  • Seed Data Module: A frozen-in-time list of pre-written, realistic orders. This is the exact spot where a real API integration would plug in later.
  • Priority Engine: The intelligence. It takes an order, applies 8 rules, and outputs a priority level and a plain-English reason. It doesn't guess; it's predictable.
  • App State: The short-term memory. It holds the current list of prioritized orders and tracks which one is selected. State resets on refresh.
  • UI: Three visual zones (Summary Bar, List Panel, Detail Panel) that simply render whatever is in the App State.

Components

js/app.js (App State)▼
The central coordinator. Holds the order list and selected order ID. Exports functions to initialize, select an order, advance status, and simulate a new order. Wires the engine to the UI components.
js/engine/priority.js▼
A pure function. Takes an order and a reference time, applies the 8 rules (first match wins), and returns the priority level and plain-English reason. Knows nothing about the UI.
js/data/orders.js▼
Exports the array of 7 pre-written seed orders and a SEED_REFERENCE_TIME constant. This is the exact seam where a real API integration connects later.
UI Components (dashboard, list, panel)▼
Dumb rendering modules. They receive state and render HTML. The panel module also handles the dynamic action button labels based on the status transition table.

Decisions & Insights

Right-side detail panel: Chosen so the seller can act without losing context of the queue.

Seed timestamps vs Date.now(): Priorities calculate against a fixed `SEED_REFERENCE_TIME`. This makes the demo predictable. Switching to real time later is a one-line change at the call site.

💡 The "Real vs Simulated" Architecture Insight In this POC, there is no real API. But the seed data module (`orders.js`) is shaped exactly like an API response.

When you add the WhatsApp Business API later, it won't change the UI, the engine, or the app state. It only replaces the static array in `orders.js` with a live fetch call.

This is a real pattern called dependency inversion — the system depends on the shape of the data, not its source.
