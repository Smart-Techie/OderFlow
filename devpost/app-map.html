OrderFlow App Map

A guide to how your proof of concept is built and where to make changes.

OrderFlow is a client-side vanilla JavaScript app that uses a frozen seed dataset to demonstrate an intelligent order operations assistant. It has no server, no database, and no build step. It relies entirely on ES Modules and a client-side state object.

To run it: Double-click index.html (or serve the folder with a local server like python -m http.server) and it works instantly.

The Code Route: Clicking an Action Button

1
js/components/order-panel.js

This UI component renders the right-side detail view. When you click the "Accept Order" button, it triggers the onActionClick callback, passing the order ID and the new status.

2
js/app.js > handleActionClick()

The central coordinator catches the click. It finds the order in state.orders, updates its status, sets the "last changed" time to our simulated current time, and then calls updatePrioritiesAndSort().

3
js/engine/priority.js > calculatePriority()

The priority engine is completely separated from the UI. It receives the updated order, applies the 8 rules, and returns the new priority level and plain-English reason. The app state then re-sorts the queue and triggers a full UI render.

To change this, start here:

  • To add a real API integration: Go to js/data/orders.js. Instead of exporting the static array, write a fetch() call that returns data in that exact same shape. The rest of the app won't know the difference.
  • To tweak the priority rules: Go to js/engine/priority.js. You can change thresholds or add new rules without ever touching the UI.
  • To change the colors or fonts: Go to css/base.css. All colors are stored as CSS variables (e.g., --critical: #f85149;) at the top of the file.
  • To add a new status transition: Update the actionMap at the top of js/components/order-panel.js.

A Practice to Reuse: Dependency Inversion (The Data Seam)

By keeping all simulated order data inside a single isolated file (orders.js) formatted exactly like a real API response, we proved the complex UI and Priority Engine behavior without needing to build a backend first.

Next time you build: Isolate your dummy data into a single module. Build your app to read that module. When you're ready for the real API, you only have to rewrite that one module, and your entire frontend will just work.
